# 独立 Qwen-14B：BC E5 → E6 同现场诊断

检查日期：2026-09-11。重点检查种子 27；使用本轮冻结的 DOPS fast 后端、固定顺序和二元设备动作。

**已定位到实质性的执行问题：E6 改变设备安排后，破坏了权重缓存复用，部分现场还把工作集中到一台设备。在带长队的真实验证现场，E6 选择全部可选算子走 NPU，造成反复加载权重。**

这能解释本次取样中的吞吐退步。它还不能证明全部模型、全部种子的退步都由同一个原因造成，也不构成 PPO 算法失效的证据；本轮检查点仍处于 BC 阶段。

## 2. 如何保证比较的是同一个现场

- 检查点：`independent/qwen_14b/bc/epoch_005/seed_27/bc_last.pt` 与 `epoch_006/seed_27/bc_last.pt`。
- 先做 batch=8、prompt=128 的控制实验，分别由冷启动、Static prefill、NPU prefill 构造现场。
- 再在真实验证 trace `burstgpt_val_000021`、1.25 倍负载上，分别让 E5、E6 推进前两个窗口。每窗口沿用原设置的 32 次 decode；共取样 14 个现场。
- 在每个取样点，两份模型使用相同的窗口决策输入及此前安排，再把生成的计划放到**同一个执行快照的副本**中运行。请求、KV、权重缓存和设备/链路时间线一致。
- 每个 E5/E6 基准计划从同一快照重复两次，阶段耗时和全部节点时间表完全一致。

原验证会在一个窗口内固定安排。因此，某些计划在窗口开始时根据较小批量生成，执行到取样点时批量已经增加到 16；本诊断保留了这一行为。下面比较的是同一阶段的模拟执行耗时，未把重新生成两份候选的诊断开销加入阶段时间。上面的正式吞吐成绩仍包含正常网络决策耗时。

| 共同执行现场 | 批量 | E5 decode | E6 decode | E6/E5 |
|---|---:|---:|---:|---:|
| 固定 NPU prefill 后，prompt=128 | 8 | 0.301386 s | 0.361190 s | 1.198 倍 |
| 真实 trace，由 E5 推进得到的已有缓存现场 | 16 | 0.031164 s | 0.171327 s | 5.498 倍 |
| 真实 trace，由 E6 推进得到的现场 | 16 | 0.327589 s | 0.718537 s | 2.193 倍 |

不能把第二行的 E5 与第三行的 E6 相除来声称“同现场加速”；它们来自不同快照。

## 3. 具体慢在哪里

### 已有缓存现场：计算更少，搬运更多

在上表第二行，E6 改变了 681 个节点的设备。代表性变化包括：28 个 `FFN_W2` 节点从 PIM0 转到 NPU、11 个从 NPU 转到 PIM1；56 个 `O` 节点从 PIM 转到 NPU。

| 计时或计数 | E5 | E6 | 差值 |
|---|---:|---:|---:|
| 一次 decode 的实际阶段时间 | 31.16 ms | 171.33 ms | +140.16 ms |
| 各设备计算时间之和 | 43.28 ms | 39.51 ms | **−3.77 ms** |
| 权重加载活动时间之和 | 0 | 159.93 ms | **+159.93 ms** |
| 权重访问未命中数 | 0/560 | 227/560 | +227 |
| 权重传输量 | 0 | 4.839 GB | +4.839 GB |

这些时间可在不同设备间重叠，不能直接相加等于阶段时间。计算时间使用 DOPS 的计算阶段记录，包含其计算后端计入的开销；没有把“权重加载+计算”的整个算子时段误称为纯计算。

设备在算子服务时段之外的时间也明显增加：PIM0 从 11.04 ms 增至 158.55 ms，PIM1 从 18.35 ms 增至 137.45 ms，NPU 从 20.82 ms 增至 25.28 ms。这些空档可能包含等待前驱、数据就绪或通信，不能全部解释为某一种独立等待。权重加载记录中的链路排队等待均为 0；这里的主要问题是加载工作本身及串行瓶颈。

### 带长队现场：NPU 缓存装不下，权重反复加载

在由 E6 推进的第二个窗口边界，已有 16 个请求运行，另有 68 个请求等待。E6 把 1040 个可选节点全部放到 NPU，PIM 仅执行固定的 KV 写入。

- 该 DAG 的 560 次带权重算子全部在 NPU，权重加载合计 **21.601 GB**。
- NPU 权重缓存容量约 **16.321 GB**，容纳不了整轮需要的权重。
- 即使现场已经执行过前一个窗口，本次 560 次权重访问仍全部未命中。
- 该步总耗时 **718.54 ms**，权重加载为 **712.48 ms**；计算合计只有 **24.99 ms**，并与加载重叠。
- 原样继续执行的 64 次 decode，每次都耗时 **0.7128–0.7195 秒**，每步通信量为 **21.63–22.22 GB**。这是持续的重复加载，而非一次冷启动开销。

可以把它理解为：桌面放不下所有课本，安排却坚持只用这一张桌子；每做下一轮题，都要把刚搬走的课本重新搬回来。NPU 的计算较快，仍抵不过反复搬运的代价。

GB 在本报告中按 10^9 字节计算。

## 4. 只改一类算子，差距能否缩小

每项试验均从原 E6 计划出发，只恢复该类中发生变化的节点，使用相同快照重新运行。

| 现场 | 改动 | 原 E6 | 改后 | 结论 |
|---|---|---:|---:|---|
| 固定 NPU prefill 后，batch=8 | 恢复 39 个 `FFN_W2` 节点 | 361.19 ms | 298.72 ms | 本组退步基本消除 |
| 真实 trace 的 E5 缓存现场 | 恢复 39 个 `FFN_W2` 节点 | 171.33 ms | 89.63 ms | 消除该组差距的 58.3% |
| 同上 | 恢复 56 个 `O` 节点 | 171.33 ms | 113.25 ms | 消除该组差距的 41.4% |
| 真实 trace 的 E6 现场 | 恢复 79 个 `FFN_W1` 节点 | 718.54 ms | 506.57 ms | 把负担分给 PIM 后减轻瓶颈 |

各行恢复试验互相独立，恢复比例不能相加来替代联合试验。在简单现场，只恢复 `FFN_W1` 虽减少了加载工作，总阶段时间仍约 361.19 ms；恢复 `FFN_W2` 才能解除 PIM1 的主要瓶颈。这说明“搬运总量减少”和“关键设备变快”也要分开判断。

## 5. 哪些输入触发了慢安排

保持真实执行快照及正在运行的 16 个请求不变，只改变提供给 E6 的部分观察信息：

| 输入对照 | 改变节点数 | decode 耗时 |
|---|---:|---:|
| 原始输入：16 个运行、68 个等待 | — | 718.54 ms |
| 仅把到达/服务速度等五项输入置零 | 0 | 718.54 ms |
| 仅把等待队列暂时设为空 | 838 | 357.16 ms |
| 同时做上述两项 | 838 | 357.16 ms |

这证明：**在本例中，排队信息能触发 E6 改变安排，并造成显著耗时变化。** 暂时遮蔽队列只是定位原因的试验；修复方案应让训练覆盖真实排队场景，并用真实验证输入验收。

当前 BC 构造的 anchor 是统一 batch/prompt 的请求：prefill 时只有 waiting，decode 时只有 active。它没有覆盖“有请求正在运行，同时有更多请求排队”的组合；真实 trace 还有混合长度、不同到达年龄、策略自己造成的缓存状态。这与正式执行的现场存在实质差距。

另一个已确认的输入缺口：到达速度、队列增长、最近服务速度等五项在 BC anchor 中均取零。检查种子 27 的 E5/E6，其对应输入权重列与随机初始化的最大差值均为 0。不过上述置零对照没有改变本例的安排，因此没有把这五项当成此次退步的直接原因。

## 6. 为什么 loss 下降仍会变慢，以及下一步

BC loss 衡量的是：在已有训练现场，模型给历史示范动作多高的概率。较快示范得到较大的训练权重，但这种快慢来自已有 anchor 的候选评分。它不会直接因为真实回放中“重新搬了多少权重、队列状态下是否选错设备、后续 32 次 decode 是否持续变慢”而扣分。

此次已确认的链条是：**E6 在部分真实现场生成了不同安排 → 权重缓存复用下降或工作集中到单个设备 → 加载和设备瓶颈增加 → 吞吐下降。** 在带长队的现场，输入对照进一步证明队列信息能够触发这类安排。训练数据覆盖不足与这些现象一致；需要补数据后的对照来检验改善幅度。

建议优先做一个有限修复试验：

1. 从固定的训练 trace 中收集 Static、E5 和当前策略实际经过的现场，重点补“运行+排队”、混合长度及不同缓存状态；继续使用当前 DOPS fast 后端重新评分。
2. 对容易反复加载权重的候选，补看连续几步 decode 的耗时和缓存复用，避免只依据单次冷/热阶段评分判断好坏。
3. 先做一个模型、一个种子的 BC 对照，按原固定验证集的实际吞吐验收，再决定是否扩大。E5 保留作对照，PPO 仍遵守既定 BC 验收门槛。

网络加深、扩大 PPO 训练轮数都还没有被本次证据支持为首要修复方向。当前更直接的问题是模型遇到了未被充分训练的现场，并学出了昂贵的设备安排。
