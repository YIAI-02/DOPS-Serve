# PPO 小规模性能实验（Q11）

## 目标与边界

- 测量 CPU 多进程、CPU 线程数、GPU 批量推理对当前 PPO 链路的实际影响，为后续 50 epoch 的资源方案提供依据。
- 使用 HPC 当前 critic 实验的代码、BC E0 actor、三个独立模型的 best critic。沿用 BurstGPT 连续到达、负载标定、C026 和 KV 设置。
- 正式代码、训练入口、协议和 checkpoint 不修改；不启动正式 PPO。优化器测速只更新临时内存中的模型副本。

## 执行

| 实验 | 固定工作量 | 比较项 |
|---|---|---|
| CPU 并行回放 | 7B；train trace 384/628 × 负载 0.5/1/1.5 × seed 4/15，共 12 个任务；每任务预热 8 plan 后测 64 plan | 1/3/6/12 进程各两轮，第二轮反序；进程内单线程 |
| 策略推理 | 三个模型；已完成 train trace 315 的开头/中段/尾段真实输入；actor sample + logprob + critic | CPU 1/2/4/8 线程，batch=1；GPU batch=1/3/12；预热 2 次，测 3 次 |
| PPO 更新 | 7B；三负载各连续采样 16 plan，使用 critic bootstrap；每次恢复相同起点 | CPU 单线程/GPU，各 3 次；仅测一次 PPO pass，4 个 optimizer step |
| 模拟器热点 | 7B、trace 384、load=1，推进 32 plan 后 profile 后续 32 plan | `env.step` 的累计耗时调用栈 |

CPU 作业申请 12 核、最长 1 小时；GPU 作业申请 1 GPU + 8 核、最长 30 分钟。全部通过 Slurm 在 compute 节点执行。

## 口径和最小验收

- 多进程比较同一工作量；单独报告进程启动与测量耗时，逐任务核对阶段、输出 token、完成数、模拟时间和最终动作一致。
- 多进程实验返回精简统计，不含正式训练的完整 rollout 数据传输、权重广播和更新等待；其加速比只用于判断回放并行潜力。
- CPU/GPU 均使用 TorchScript actor、相同权重与输入；GPU 计时前后同步。分别报告设备驻留和含传输/列表输出的耗时；后者不含构造环境输入的时间。
- GPU 的 `fixed_from` 保持 CPU 控制元数据，避免逐节点搬运标量引入额外同步。通过相同动作的 teacher-forcing 比较 logits/value 数值。
- 并行回放是 trace 启动段性能实验，报告实际 batch/KV 范围；不能代表整条 trace 的训练质量或完整耗时。
- 更新测速调用当前函数，仍是 pass 末检查 KL；不代表已实现讨论中的每 minibatch 检查 KL。
- 完成后保留指标、profile 和日志；删除本地与 HPC 的临时 Python/Shell 助手。

|---|---|---:|

### CPU 并行回放

下表每格都完成相同的 12 个任务，耗时包含任务重置与每任务 8 plan 预热，不含启动进程池的 2.2–5.2 秒。

| 进程数 | 第一轮 / 秒 | 第二轮 / 秒 | 相对单进程加速 |
|---:|---:|---:|---:|
| 1 | 397.73 | 395.95 | 1.00× |
| 3 | 136.45 | 136.11 | 2.91× |
| 6 | 68.89 | 68.55 | 5.77× |
| 12 | 36.68 | 36.94 | 10.78× |

全部 8 次运行均通过逐任务一致性检查。相对当前 PPO 已有的 3 个回放进程，12 进程的本次加速是 **3.70×**。这证明独立环境适合多进程并行，但没有验证正式 PPO 的采样同步或收敛。

实际覆盖 batch=1–16、KV 长度 0–2784；trace 384 混合 prefill/decode，trace 628 测量段全部是 batch=16 的 decode。仍未覆盖最大长度 7315 或长 trace 的完整尾段。

### 策略推理与参数更新

下表使用已通过一致性检查的严格 FP32 补测：三个真实时点的中位耗时，包含张量传输和输出转列表，单位为毫秒/plan。GPU batch=12 采用同一真实输入重复成批，数字是整个批次耗时除以 12。

| 模型 | CPU 1 线程 / batch=1 | CPU 8 线程 / batch=1 | GPU batch=1 | GPU batch=12 摊销 |
|---|---:|---:|---:|---:|
| 1.8B | 169.0 | 113.2 | 204.2 | 18.3 |
| 7B | 170.5 | 114.4 | 204.5 | 18.4 |
| 14B | 240.3 | 160.5 | 288.6 | 25.9 |

- 单个回放的策略推理开 8 线程约提速 1.5×，需要占用更多核；逐条搬 GPU 比 CPU 单线程还慢约 20%。
- GPU 大批次有吞吐优势，但尚未实现多个真实环境的集中采样、排队和传输，不能把表中摊销值当作完整回放耗时。
- 7B 单次 PPO pass（三负载各 16 plan、4 次 optimizer step）：CPU 三次为 10.068 / 9.795 / 9.831 秒；GPU 为 3.088 / 1.147 / 1.148 秒。GPU 首次有初始化开销，预热后约快 **8.6×**。
- **严格 FP32 的 CPU/GPU 数值一致性为 9/9 通过**，覆盖三个模型的开头、中段、尾段输入。最大 logits 差异为 `9.54e-6`，最大 value 差异为 `1.97e-6`，检查使用 `atol=2e-5, rtol=1e-4`。
- 同一批 PPO 更新的最终 KL：CPU `0.00019754134`，GPU `0.00019754171`；value loss 分别为 `0.030239209`、`0.030239249`。本次短更新数值接近，不等同于保证完整随机训练轨迹相同。
- 补测设置：`torch.backends.cuda.matmul.allow_tf32=False`、`torch.backends.cudnn.allow_tf32=False`、`torch.set_float32_matmul_precision("highest")`；容器内 `NVIDIA_TF32_OVERRIDE=0`、`TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=0`。
- 首轮默认精度 0/9 通过的原始结果继续保留：最大 logits/value 差异分别为 `0.002658` / `0.000458`。后续正式运行建议采用本次通过检查的严格 FP32 设置。

### 模拟器热点与待讨论修改

32 次 `env.step` 的 profile 共约 5400 万次调用。主要热点是调度器 `_earliest_finish_on_device`，其中 `RaggedCostModel.estimate_activation_bytes` 被调用 155000 次、累计 12.03 秒；底层 activation 估算累计 9.24 秒。累计时间存在嵌套，不能相加推算可节省时间；profile 本身也有开销。

最小候选是：每次 `configure_requests` 预先计算请求长度分组；同一次请求形状下复用原 node 的 activation 字节估算。每次 `configure_requests` 必须失效，包括一次 `env.step` 内自动复用 plan 的后续 decode。设备排队、通信、权重命中和完成时间仍完整计算。此项已核对代码依赖，**尚未修改或测速**。

## Q11 建议

1. **采用 CPU 多进程回放 + GPU 严格 FP32 更新。** 每个回放 worker 内保持 1 个 PyTorch 线程，优先用多核增加独立环境数。
2. **12 个回放进程作为下一步并行配置候选。** 相对已有 3 进程，冻结回放实测快 3.70×；尚需真实 PPO 链路验证数据传输、权重同步、负载等待和更新开销。
3. **保留每负载每轮 16 plan、minibatch=4 的已讨论合同。** 扩 worker 数不能直接把每轮总采样量从 16 放大到 64；多环境如何分配这 16 plan、截断位置和 bootstrap 必须先讨论。三个 seed 并行也不等于单个 seed 的 epoch 加速。
4. **第一版策略逐条采样继续放 CPU。** 集中 GPU batch=12 只是潜在优化，当前没有端到端证据支持为它增加采样服务与同步机制。
5. **优先讨论模拟器的重复纯计算去重。** 先在一次 `configure_requests` 范围内复用请求统计和 activation 字节数，保留动态调度语义；通过固定动作回放比对后，再测完整 PPO 的实际加速。

50 epoch、32 条完整训练 trace 和种子 4/15/26 保持已讨论目标。本次不是完整训练试跑，不能据此承诺 50 epoch 的总耗时或收敛效果。生产修改仍需先讨论；后续所有代码修改在本地完成、保留已有中文注释，经 data 上传并逐文件比较一致后再提交 HPC 作业。
