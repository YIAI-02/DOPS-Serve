# 逐 token 模拟优化建议

目标：减少 CPU 回放耗时，优先保持现有模拟语义、PPO 奖励和策略决策频率。当前仅完成代码检查与本地短剖析，尚未修改正式代码或提交新的优化实验。

## 已有证据

- 完整短 trace 对照中，stride=2 的模拟器耗时占回放约 77.8%；改策略 stride=16，累计墙钟仅减少约 8%，且 7B、1.5× makespan 发生变化。
- 本地原始代码分别回放 1.8B、7B 的同一真实请求（prompt 352、output 40），只对 env.step 做 cProfile。两次均含 1 次 prefill 和 39 次 decode。
- RaggedCostModel.estimate_activation_bytes 各调用 141,040 次，累计剖析耗时 3.487/3.481 秒，约占 35.5%/36.0%。该比例包含子调用，不能与其子函数耗时相加。
- plan.normalize 约 0.016 秒，详细算子记录入口约 0.058 秒；图索引已经缓存。优先优化成本重复计算，不先重做图索引或仅删除日志。
- 剖析器有额外开销，以上是定位证据，不能当作优化后的加速比或完整 trace 的耗时分布。

## 推荐的最小改动

1. 先仅在 `artifacts/burstgpt_ppo_20260916/code/src/dops_serve/placement_cost.py` 的 RaggedCostModel 中验证每步成本缓存：同一 token、同一节点与相同输入形状的激活字节数/FLOPs只算一次；configure_requests 时清空。缓存键必须覆盖实际参数，内部 primitive 调用保持现有语义。
2. 每个 token 仍推进 KV、设备与链路状态、到达、准入和完成；策略 stride 保持 2。完整调度结果、依赖权重驻留和通信占用的结果不直接跨状态复用。
3. 第一项通过后，再考虑跨 token 缓存 batch 不变时的非 attention 固定成本；QK/SV、KV 读取等随上下文长度增长的部分保持精确更新。

## 类似 stride 的进一步方案

每隔 4/8/16 token 完整模拟一次、用首步耗时乘步长或插值补中间 token 属于近似回放，不能预先保证 makespan、排队与奖励不变。即使做分段推进，也必须停在策略决策、请求到达/完成和其他会影响成本的状态变化边界。当前策略 stride=2，能够直接合并的跨度也受该边界约束；不能保持原策略决策却直接跳过 8 token 的状态。

若要探索近似回放，应另外确定可接受误差，用完整逐 token 回放验证，不能按本次“makespan 不变”的授权直接替换 PPO。

## 验收与工件

- 先用同一输入和固定策略做本地旧/新对照，再经 data 上传、逐文件读回核对后提交 HPC 对照。
- 要求计划序列、每请求完成时间、输出 token 数、KV/内存状态、makespan 和奖励一致；再比较关闭 profiler 后的重复测量墙钟耗时。
- 保留现有网络、checkpoint、训练数据和学习参数；保留全部中文注释。实际改代码前继续按用户要求讨论确认范围。
- 本地剖析证据：`artifacts/burstgpt_replay_profile_20260917/`，含两份 pstats、文本热点表、metrics、profile_summary.json 和日志。没有创建或遗留一次性助手源文件。
