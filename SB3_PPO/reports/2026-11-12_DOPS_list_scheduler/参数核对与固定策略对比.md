# Bifocal 参数核对与固定策略对比

日期：2026-11-12。以下均为本地 fast 模拟结果，单位 ms。诊断 seed=0，不是多 workload 调参结论。原 PPO 训练代码、模型与仓库默认参数均未修改。

## 结论

基础环境参数一致，但上次 138.789466 ms 的 Bifocal 试跑关闭了仓库默认开启的 decode 摊销，也没有启用前瞻。恢复仓库默认摊销后，原生结果为 108.013333 ms。默认摊销使用真实剩余 decode 长度，所以只作为单独的诊断对照，不能混入“不知道真实输出长度”的实验。

统一到 PPO 使用的成本模型、KV ledger、forward 边界和 AllReduce 计时后，上次设置得到 138.969641 ms，全 PIM 为 63.517819 ms。主要差距不是 fast 开关或计时路径，而是 prefill 的局部选择没有充分考虑后续 decode 复用：只把 prefill 改成全 PIM，再让 Bifocal 自由调度 decode，完整请求降至 63.522255 ms。

## 配置是否一致

12 份正式训练的 `environment_config.json` 与当前 `configs/environment.json` 完全相同。与上次 Bifocal 配置逐字段比较，下列基础参数均一致。

| 项目 | 两边实际设置 |
| --- | --- |
| 模型 | Qwen 1.8B，28 层，FP16 |
| 请求 | batch=1，prefill=64，decode=64 |
| 分片 | tp_qkv=2，tp_ffn=2 |
| 硬件 | 同一个 `hardware_1npu_2aim.json`，1 NPU + PIM0/PIM1，FC 互连 |
| 计算后端 | npu_backend=fast，pim_fast_mode=true |
| 权重 | host 来源，ND 存储，初始冷缓存 |
| 重叠系数 | WEIGHT_LOAD_COMPUTE_OVERLAP_RATIO=1.0；PIM_WEIGHT_LOAD_OVERLAP_RATIO=0.5 |

共有 37 个源码/配置文件可以在下载仓库与 PPO backend 间对应：36 个逐字节一致；`scheduler_base.py` 唯一差异是把循环里的 `set(order_iter)` 提前计算，属于 Python 执行效率优化，不改变模拟时间。核对明细见 `parameter_audit/config_audit.json`。

仍需区分以下执行规则：

| 项目 | PPO 训练 | 原生 DOPS CLI |
| --- | --- | --- |
| 成本模型 | RaggedCostModel，按实际 query/KV 长度配置 | CostModel |
| 时间推进 | 每个完整 forward 有起始时间下界 | 原生 scheduler 时间推进 |
| AllReduce | ContinuousScheduler 显式占用 FC 链路 | 原生 collective 路径 |
| decode 更新 | token 0、4、8…60 | token 0、1、4、8…60 |
| 放置/顺序 | 28 层共享 9 个二元选择，固定拓扑序及小算子跟随 | 可逐节点、逐分片放置，并选择 ready 节点顺序 |

## Bifocal 参数是否生效

| 参数 | 仓库默认 | 上次试跑 | 实际含义 |
| --- | ---: | ---: | --- |
| SCHED_JOINT_LK_ENABLE | true | true | 只是允许前瞻，不能单独保证启用 |
| SCHED_JOINT_LK_H | 3 | 3 | 前瞻链最多 3 个算子，不是 3 个 decode token |
| SCHED_JOINT_LK_GAMMA | 0 | 0 | `gamma>0` 才进入前瞻；当前前瞻实际关闭 |
| SCHED_JOINT_LK_CONSIST_LAMBDA | 0 | 0 | 一致性惩罚为零 |
| SCHED_JOINT_LK_PLAN_HINT_MAX | 3 | 3 | 最多保存 3 个前瞻节点提示 |
| SCHED_WEIGHT_BIAS_ETA | 0.1 | 0.1 | prefill 权重复用偏置，形式为 `-eta * t_reload` |
| SCHED_DECODE_AMORT_ENABLE | true | false | 上次按“未知真实输出长度”的约定显式关闭 |
| 摊销 alpha / rmin / reuse_prob | 1 / 1 / 1 | 关闭时无作用 | 默认剩余 token 数来自真实 decode 总长度 |
| scheduler_seed | 配置文件指定 | 0 | 相同评分时可能随机打破平局 |

这里的 lookahead gamma 与 PPO 折扣 gamma=1 是两个不同参数。PPO 学习率、GAE、batch size 等训练参数不适用于列表调度器。

前瞻参数通过 `config.py → scheduler_common → scheduler_bifocal` 导入；当前 `_apply_runtime_config_overrides()` 只处理两项重叠系数。因此，只往运行 JSON 添加同名 H/gamma/eta 字段并不能使它们自动生效。此次探针在独立进程导入调度模块之前设置参数，且记录实际调用数：默认前瞻调用为 0，H=3/gamma=0.4 时前瞻函数调用 87,393 次。

另有一个需要后续设计时注意的行为：`BifocalScheduler.reset_state(clear_caches=False)` 仍清空 `_weight_plan_hint`。原生每次 `schedule()` 也调用该方法，因此物理权重缓存保留，但上一 token 的权重提示不保留。lambda=1 的单项试跑没有改善；不能仅凭增大 lambda 便认为启用了跨 token 一致性。

代码位置：

- `DOPS/src/config.py:168`：调度参数。
- `DOPS/src/scheduler/scheduler_bifocal.py:958`：前瞻实际启用条件。
- `DOPS/src/scheduler/scheduler_bifocal.py:1040`：EFT、前瞻、复用和摊销的合成评分。
- `DOPS/src/scheduler/scheduler_bifocal.py:128`：摊销开关与剩余输出长度。
- `DOPS/src/scheduler/scheduler_bifocal.py:33`：每轮清空提示。

| 策略 | Prefill | Decode | 总时间 |

| 全 NPU 固定策略 | 86.622866 | 193.232694 | 279.855560 |

三个固定策略及 PPO best 均复现已有正式结果。另把四组 Bifocal 生成的完整节点计划交给 `PrefixExecution` 独立回放，只使用导出的节点顺序和放置，四组耗时均与生成时完全一致；记录见 `parameter_audit/replay_validation.json`。

原生路径下也复现同一现象：上次 Bifocal 为 138.789466，全 PIM 的相同固定放置为 63.510553。不能把当前问题主要归因于原生/PPO 计时差异。

## 为什么当前选择会吃亏

Bifocal 原设置的 prefill 比全 PIM 快 0.955417 ms，但 decode 慢 76.407239 ms。只改 prefill 为全 PIM、保留后续列表调度，端到端改善 75.447386 ms。

具体看 `L0_FFN_W3_s0`：prefill 的即时完成时间估计为 NPU 0.642874 ms、PIM0 0.649174 ms，NPU 略早；eta=0.1 的偏置未逆转选择。到第一个 decode token：

| 设备 | 权重状态 | 当前无排队服务代价 | 驻留后服务代价 |
| --- | --- | ---: | ---: |
| NPU | 已缓存 | 15.659898 μs | 15.659898 μs |
| PIM | 尚未缓存 | 460.248975 μs | 2.867200 μs |

于是贪心 EFT 继续选择 NPU：它避开眼前的一次加载，却没有在 prefill 阶段充分计入后面许多次更低的 PIM 服务代价。只考虑未来 4 次复用不足以逆转本例的迁移选择。完整评分探针保存在 `parameter_audit/ppo_bifocal_probe.json`，插入探针后的总耗时与无探针结果一致。

prefill 的复用偏置本身使用的是 `-eta * t_reload`，并非对未来完整请求代价的精确评估；前瞻则是一个最多 H 个算子的、忽略链外依赖的近似链估计。这解释了为什么“开启前瞻”或“叫 Bifocal”不等于它必定超过固定策略。

## 下一步建议

1. 后续性能对比统一使用当前 PPO 的成本与连续执行规则，单列真实输出长度可见的 oracle 结果。
2. 优先改进 prefill 到 decode 的复用评分：使用固定或预估的复用窗口，显式比较不同设备的冷启动与驻留服务代价；不把真实输出长度作为策略输入。
3. 把全 PIM、全 NPU、Prefill NPU / Decode PIM 也纳入离线候选集合，并用同一个完整回放选择最短候选。如果要求选出的结果至少不差于这些固定策略，需要显式包含它们；单次贪心调用没有这种保证。
4. 在决定正式实验前，明确是否继续允许逐层/逐分片放置和自由排序。当前诊断没有解决“相同动作空间”的比较问题。
